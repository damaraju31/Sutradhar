# Context Refresh

Verifies the health of the project's context hierarchy and proposes updates.

## Process

### Step 0: Health Score Baseline

Run the health score evaluator. Handle self-healing for missing/stale manifest:

```bash
bash ~/.claude/skills/project-init/scripts/context-health-score.sh --json --log
```

**Handle exit codes:**
- **Exit 0**: Score computed. Read the JSON and proceed to Step 1.
- **Exit 2**: Not bootstrapped. Run `/project-bootstrap` first, then retry.
- **Exit 3**: Manifest missing. Spawn a **haiku** agent to generate it:
  - Read the manifest generator prompt at `${CLAUDE_SKILL_DIR}/references/manifest-generator-prompt.md`
  - Spawn the agent with that prompt
  - After manifest is generated, retry the health score
- **Exit 4**: Manifest stale (project structure changed). Same as exit 3 — regenerate manifest, then retry.

Once you have a successful score, read the JSON output:
- **Coverage score**: which domains are missing rules (focus exploration here)
- **Freshness score**: which context files are stale (focus updates here)
- **Accuracy score**: which references are broken (fix these first — wrong context is worse than missing)
- **Completeness score**: which context files are scaffolded but unfilled
- **Composite score**: the overall health number to beat

Use this data to PRIORITIZE Steps 2-4 below. Start with the lowest-scoring dimension.

After completing all updates, run the health score again to measure improvement. Report both scores: "Health: {before} → {after} ({delta})".

### Step 1: Inventory (what context exists)

Read all context files and build an inventory:
- List all `.claude/rules/*.md` files with their `paths:` patterns
- List all `.claude/context/components/*.md` files
- List all `.claude/context/decisions/ADR-*.md` files
- Read `CLAUDE.md` to understand the project overview

### Step 2: Coverage Analysis (what's missing)

Spawn an Explore agent to scan the codebase:
- List all top-level source directories
- For each directory with 3+ source files: check if a matching rule file exists
- For each rule file's "Deep Dives" section: check if referenced component files exist
- Report: domains without rules, components referenced but not documented

### Step 3: Staleness Detection (what's outdated)

First, check if `.claude/context/_modifications.log` exists (maintained by the context-maintenance hook). This log records which directories were modified and when. Use it to focus staleness detection on recently-changed areas.

**Post-bootstrap first run**: If context files were just generated by `/project-bootstrap`, all have the same modification timestamp. In this case, `_modifications.log` is the primary staleness signal — not file mtime comparison. If `_modifications.log` doesn't exist yet (no edits since bootstrap), compare context file dates against **git log** dates for each domain's most recent commit instead.

For each rule file and component file:
- Primary signal: `_modifications.log` entries for the domain since the context file was last updated
- Secondary signal: compare the file's modification date against the newest source file in its domain (via `git log -1 --format=%ct -- {domain}/`)
- If the source code is significantly newer (30+ days), flag as potentially stale
- For component files: check if documented "Known Gaps" reference code patterns that no longer exist (grep for documented function names, class names, or patterns)
- Report: potentially stale context files with specific concerns

### Step 4: Decision Audit (what's undocumented)

Spawn an Explore agent to scan recent git history:
- Look at commits from the last 30 days (or since last refresh)
- Identify commits that look like architectural changes (schema migrations, new service patterns, dependency additions, configuration changes)
- Cross-reference against existing ADRs
- Report: significant changes that may warrant an ADR

### Step 5: Report and Propose

Present findings to the user:

```
## Context Health Report

### Coverage
- ✅ Domains with rules: ingestion, analytics, email, core
- ❌ Domains without rules: scripts (4 source files)

### Staleness  
- ⚠️ .claude/rules/ingestion.md — last updated 45 days ago, 12 source files changed since
- ⚠️ .claude/context/components/dispatcher.md — references `process_and_commit()` which was renamed

### Missing Documentation
- Component `core/entity_resolution.py` (287 lines, 5 exported functions) has no component file
- 3 recent commits look like architectural decisions with no ADR

### Suggested Actions
1. Create rule file for `scripts/` domain
2. Update ingestion rule file (review for accuracy)
3. Create component file for entity_resolution
4. Review 3 commits for potential ADRs: [commit hashes]
```

### Step 6: Apply (with user approval)

For each suggested action, ask the user:
- "Should I create/update this?" (yes/no/skip)
- For updates: show the proposed change before applying
- For new files: use the `/context-create` skill to scaffold from templates

## Automation

This skill can be run:
- **Manually**: `/context-refresh` at any time
- **Periodically**: Suggest running after each sprint or milestone
- **Automatically**: A SessionStart hook could run a lightweight version (staleness check only) and surface warnings
