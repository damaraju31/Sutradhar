# Context Hierarchy

> Operational guide to the three-layer context system. For *why* it exists, see `DESIGN_RATIONALE.md`. For *how to use* the framework end-to-end, see `USAGE.md`.

The hierarchy gives every agent the right amount of context at the right time — without paying token costs for information that isn't needed.

---

## The three layers at a glance

```
L0 — CLAUDE.md                     always loaded (every agent, every session)
L1 — .claude/rules/*.md            auto-loaded when an agent reads a matching file
L2 — .claude/context/              on-demand only (agent reads explicitly)
       components/*.md
       decisions/ADR-*.md
```

| Layer | Purpose | Loading | Size cap |
|-------|---------|---------|----------|
| **L0** | Project identity, critical rules, cultural DNA, navigation pointers | Auto, every session start | ≤100 lines |
| **L1** | Domain-specific patterns, constraints, integration points | Auto when agent reads a file matching `paths:` glob | ≤50 lines per rule |
| **L2 (component)** | Deep internals, known gaps, edge cases | On-demand (agent decides to read) | ≤150 lines per file |
| **L2 (ADR)** | Architectural Decision Record — context, decision, rationale, evidence | On-demand | ≤30 lines per file |

Worst case (every layer loaded simultaneously): **~940 lines**, well under the 200k window.

---

## L0 — `CLAUDE.md`

The single file every agent sees on every turn. Lives at the project root.

**Contents (in order, by section):**
1. Project identity — name, description, tech stack
2. How We Work — cultural principles (12 traits, ~20 lines)
3. File map — where to find PROJECT_STATE, team dirs, tasks, agent memory
4. Recovery protocol — what to read on session start
5. State update protocol — how teams report state via `STATE_UPDATE.md`
6. Active teams — which teams are activated for this project
7. Coding conventions — stack-specific (filled by user during init)

**What does NOT belong in L0.** Implementation details, file-specific gotchas, decision rationale. Those live in L1 or L2.

**Generated by:** `scripts/init.sh` (composes `CLAUDE.md.base.template` + optionally `CLAUDE.md.teams.template`).

## L1 — Domain rules

One file per domain that has its own conventions. Lives at `.claude/rules/<domain>.md`.

**Trigger model.** Each rule file declares a `paths:` glob in its frontmatter. When an agent uses `Read` on a file matching the glob, the rule auto-loads into context. Rules do **not** fire on `Grep` or `Glob` — searching shouldn't inflate context.

**Frontmatter schema:**

```yaml
---
name: backend-api-conventions
description: Patterns and constraints for the FastAPI backend
paths:
  - "backend/api/**/*.py"
  - "backend/services/**/*.py"
---
```

**What goes in a rule.** Naming conventions, error-handling idioms, library quirks, integration points to flag, "if you're touching X always also update Y" rules.

**What does NOT.** Per-file detail (that's L2 component context), high-level architecture (that's L0 or an ADR).

**Provenance.** Every rule file ends with a `## Provenance` section. Every meaningful update appends a date + brief summary. The health-score evaluator uses this for freshness checks.

**Templates:** `framework/templates/context/rule.md.template`.

## L2 — On-demand context

Two file types. Both live under `.claude/context/`.

### Component files (`.claude/context/components/<name>.md`)

Deep internals of a single component or module. Read only when an agent is actively working on that component.

Sections:
- **Summary** — one paragraph, what it is and what it owns
- **Surface area** — public API, entry points
- **Internals** — non-obvious implementation details, why decisions were made
- **Known gaps / limitations** — what doesn't work yet, what's hacky, what to revisit
- **Provenance** — update log

### ADRs (`.claude/context/decisions/ADR-NNN-<slug>.md`)

Architectural Decision Records. Capture a decision, its context, alternatives considered, and the chosen path. Read by agents that need to understand *why* the codebase looks the way it does.

Sections (compact — ≤30 lines):
- **Status** — proposed / accepted / superseded by ADR-NNN
- **Context** — what triggered this decision
- **Decision** — what we chose
- **Alternatives** — what we rejected and why
- **Evidence** — links, benchmarks, references that informed the choice

**Templates:** `framework/templates/context/component.md.template`, `adr.md.template`.

## How files get created

Three paths into the hierarchy:

1. **Bootstrap a new or existing project** — `/project-bootstrap` runs a five-phase pipeline (Haiku scan → 4 parallel Sonnet analyzers → Opus synthesis → Sonnet generation → Sonnet validation) and writes the entire L0/L1/L2 tree from the project's actual code. See `framework/skills/project-bootstrap/SKILL.md`.

2. **Add a new rule or ADR mid-flight** — `/context-create` walks you through writing a single new entry against the templates.

3. **Coding agents update context as a side effect of work.** Every Frontend or Backend agent task produces *two outputs*: a code change AND a context update. Changed a pattern → update the matching rule file. Made a non-obvious decision → write an ADR. This rule is enforced socially (in the agent prompts), not by hooks.

## Keeping the hierarchy honest

Context that drifts from code is worse than no context — it confidently misleads the next agent that reads it. Three mechanisms keep drift bounded.

**1. Context-maintenance hook (`framework/hooks/context-maintenance.sh`).**
Fires on every `PostToolUse:Edit|Write`. Logs the modified source directory to `.claude/context/_modifications.log`. This is the input signal for "what context might be stale."

**2. Health-score evaluator (`scripts/context-health-score.sh`).**
A 636-line bash/python script that grades the hierarchy on a 0-100 composite scale. Runs *outside* the agent — it's static analysis, the LLM can't game it. Four dimensions:

| Dimension | Weight | Measures |
|-----------|--------|----------|
| Coverage | 25% | All source domains in the manifest have matching rule files |
| Freshness | 30% | Context files are newer than their source code (uses `## Provenance` dates first, falls back to `git log`, then mtime) |
| Accuracy | 30% | Backtick-wrapped class/function/path references in context files actually exist in source |
| Completeness | 15% | Files have non-placeholder summaries, non-empty Provenance, populated Limitations / Evidence sections |

Run with `--json` for CI use, `--verbose` for human reading, `--log` to append to history.

**3. Refresh skill.**
`/context-refresh` reads the modifications log and the health score, identifies the stalest files, and walks you through updating them.
