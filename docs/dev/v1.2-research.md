> Comprehensive research, analysis, and decisions from the V1.2 planning session (2026-03-13)

## 1. Objective

Incorporate organizational culture principles from top tech companies (Amazon, Netflix, Meta, Apple, Microsoft) plus context engineering best practices into the Agent Team Framework. The goal: every agent in the swarm (predefined, custom, temporary) embodies these traits as DNA and operates with context-awareness for quality, cost, and efficiency.

## 2. Source Culture Principles Analyzed

### Amazon's 16 Leadership Principles (Full Text Retrieved)

1. **Customer Obsession** — Start with the customer, work backwards. Earn and keep trust.
2. **Ownership** — Think long term. Don't sacrifice long-term value for short-term results.
3. **Invent and Simplify** — Expect innovation, always find ways to simplify.
4. **Are Right, A Lot** — Strong judgment, good instincts, seek diverse perspectives.
5. **Learn and Be Curious** — Never done learning, curious about new possibilities.
6. **Hire and Develop the Best** — Raise the performance bar, recognize exceptional talent.
7. **Insist on the Highest Standards** — Relentlessly high standards, deliver high quality.
8. **Think Big** — Bold direction that inspires results. Think differently, look around corners.
9. **Bias for Action** — Speed matters. Many decisions are reversible — don't over-study.
10. **Frugality** — Accomplish more with less. Constraints breed resourcefulness.
11. **Earn Trust** — Listen attentively, speak candidly, treat others respectfully. Vocally self-critical.
12. **Dive Deep** — Operate at all levels, stay connected to details, audit frequently, be skeptical.
13. **Have Backbone; Disagree and Commit** — Respectfully challenge decisions when you disagree, then commit.
14. **Deliver Results** — Focus on key inputs, deliver with the right quality, timely.
15. **Strive to be Earth's Best Employer** — Safer, more productive, diverse work environment.
16. **Success and Scale Bring Broad Responsibility** — Create more than you consume, leave things better.

### Netflix Culture Principles Analyzed

- **Context, not Control** — Leaders empower rather than micromanage. Provide context and constraints, not step-by-step instructions.
- **Highly Aligned, Loosely Coupled** — Independence while focusing on shared goals. Teams coordinate without tight coupling.
- **Radical Candor/Honesty** — Speak candidly, flag risks honestly, be self-critical.

### Meta Culture Principles Analyzed

- **Focus on Long-Term Impact** — Think beyond the immediate task. Consider downstream and future consequences.
- **Build Awesome Things** — Aspire to build something genuinely great, not just functional.
- **Live in the Future** — Forward-thinking, anticipate how things will evolve.

### Apple Culture Principles Analyzed

- **Deep Collaboration** — Cross-functional teamwork is not optional, it's core.
- **Extreme Attention to Detail** — Known for obsessive quality standards at every level.
- **Simplicity** — Eliminate the unnecessary. Complexity is a design failure.

### Microsoft Culture Principles Analyzed

- **Growth Mindset** — Learn from mistakes, update your approach, embrace curiosity.
- **Diverse and Inclusive** — Seek different perspectives before deciding.

### User's Principle (Most Important Addition)

- **Strategic Planning → Precise Execution** — Invest disproportionately in understanding the problem, mapping the solution space, and stress-testing the approach BEFORE committing to action. A well-planned precision strike beats a broad shotgun approach every time.

### Cascading Planning Model (Principle #3 — Deep Dive)

The "Plan Deep, Strike Precise" principle cascades through the agent hierarchy:

- **Head agents (orchestrators)** — Plan at STRATEGY level. Their entire job IS planning + delegating. Use Explore/Plan subagents for research. Create detailed task files with Pre-Gathered Context.
- **Subagents (executors)** — Receive strategic context from task file. Plan at TASK level within constraints: what approach? what order? what could go wrong? If something misaligns with strategic context → STOP and flag, don't assume.
- **Temporary agents** — Receive inline delegation context. Execute within the specific research/exploration scope. Return findings, don't make decisions.

Each level plans at their appropriate abstraction level. The quality of the whole pipeline depends on every level doing their planning well.

## 5. Distribution Architecture: 4-Layer DNA Model

### The Core Constraint

CLAUDE.md is the ONLY file guaranteed to be in EVERY agent's context (named, anonymous, temporary, teammates). Everything else is supplementary.

| Agent Type | CLAUDE.md | Own .md file | Parent Context | Memory |
|---|---|---|---|---|
| Named agent (`--agent cpo`) | Auto-loaded | Auto-loaded | N/A | If configured |
| Named subagent (Agent tool) | Auto-loaded | Auto-loaded | Only if passed inline | If configured |
| Temporary agent (built-in Explore/Plan) | Auto-loaded | None | Only if passed inline | None |
| Agent Teams teammate | Auto-loaded | Auto-loaded | None | If configured |

### The 4 Layers

**Layer 0: GENOME — CLAUDE.md "How We Work"**
- All 12 principles as compact character traits (1-2 lines each)
- Reaches ALL agents, always
- In the primacy zone of context (strong attention)
- Cached by prompt caching (near-zero marginal cost after turn 1)

**Layer 1: GENE REGULATION — spec/06-BEHAVIORAL-RULES.md**
- Design-time guidance (not a runtime file — agents never read it)
- Maps which principles are AMPLIFIED for each role:
  - Strategic agents: User-First, Plan Deep, Think Big, Strong Opinions, Seek Truth
  - Coding agents: Plan Deep (at task level), Raise the Bar, Leave it Better, Learn & Adapt
  - Review agents: Seek Truth, Raise the Bar, Dive into details

**Layer 2: CELL TYPE — Agent .md "How You Think"**
- Each agent's thinking section EMBODIES principles through domain lens
- NOT repeating or naming principles — expressing them
- CPO: "Start from user pain" (= User-First without naming it)
- Architect: "Map the full solution space before choosing" (= Plan Deep)

**Layer 3: EPIGENETICS — Task files + delegation messages**
- Principles cascade through HEAD AGENT BEHAVIOR, not text injection
- Pre-Gathered Context = structural embodiment of Plan Deep
- Task constraints = guardrails against plan derailment
- Quality of delegation determines quality of execution

### Why This Architecture

1. **100% coverage** — CLAUDE.md reaches every agent type
2. **No duplication** — Stated once in CLAUDE.md; agent files express, not repeat
3. **Token efficient** — ~600 tokens added to cached prefix (near-zero cost)
4. **Cascading by design** — Head agents' good behavior naturally transmits to subagents
5. **Maintainable** — Update in ONE place (template). Agent expressions are stable.

## 6. Context Engineering Research Findings

### Validated Constraints

**6.1 Context Window Limits**
- Claude models: 200k token standard window
- Claude Code auto-compaction triggers at configurable threshold
- Framework sets `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=0.85` → ~170k tokens
- Compaction is LOSSY — summarizes, potentially losing subtle but critical context
- context-recovery.sh hook re-injects only PROJECT_STATE.md after compaction
- Source: [Claude Code Best Practices](https://code.claude.com/docs/en/best-practices)

**6.2 Head Agent Context Budget**
- Fixed overhead: ~10,500 tokens (system prompt + CLAUDE.md + agent .md + tool defs) — CACHED after turn 1
- Session init: ~4,000 tokens (PROJECT_STATE + TEAM_BRIEF + memory)
- Working budget: ~185k tokens for actual work
- Each subagent delegation cycle: ~3-5k tokens (spawn + receive result)
- After ~30-40 delegation cycles → compaction triggers
- Head agent context is the bottleneck — accumulates all exploration results and subagent summaries

**6.3 Model Cost Structure**
- Source: [Anthropic Pricing](https://platform.claude.com/docs/en/about-claude/pricing)

| Model | Input/MTok | Output/MTok | Cache Hit/MTok | Relative to Haiku |
|-------|-----------|------------|----------------|-------------------|
| Opus 4.6 | $5 | $25 | $0.50 | 5x |
| Sonnet 4.6 | $3 | $15 | $0.30 | 3x |
| Haiku 4.5 | $1 | $5 | $0.10 | 1x (baseline) |

- Current framework tiering is cost-optimal: Opus for strategy, Sonnet for coding, Haiku for exploration
- Prompt caching: static prefix cached after turn 1 at 0.1x cost. Adding principles = near-zero marginal cost.
- Cache hit = 90% discount on input tokens

**6.4 Garbage In = Garbage Out**
- Direct quote from [Anthropic's context engineering guide](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents): "When agents behave badly, it's often because the rest of the input is messy — old messages, wrong retrieved docs, missing tool details, or vague system rules."
- Task file quality is THE determinant of subagent quality
- Stale tool results degrade output quality
- Compaction summaries can introduce imprecision

**6.5 Lost-in-the-Middle Effect**
- Source: [Liu et al., 2023 — "Lost in the Middle"](https://arxiv.org/abs/2307.03172)
- Performance follows U-shaped curve: highest at beginning (primacy) and end (recency)
- Middle context gets weakened attention
- [2025 MIT/OpenReview research](https://openreview.net/forum?id=XSHP62BCXN): this is an inherent architectural property, not a fixable bug
- Larger models (Opus) distribute attention more evenly but effect persists
- For our framework: CLAUDE.md is in primacy zone (good), recent task in recency zone (good), old exploration drifts to weak middle (problem)

**6.6 Prompt Caching Mechanics**
- Source: [Anthropic Prompt Caching Docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Prefix matching: system prompt + CLAUDE.md + agent prompt cached across turns
- Cache hit = 0.1x base input (90% discount)
- Cache write (5-min) = 1.25x base input
- Adding ~600 tokens of principles to CLAUDE.md: effectively free after turn 1
- Up to 90% cost reduction and 85% latency reduction for repeated prefixes

### Context Engineering Principles from Anthropic's Guide

1. **Just-In-Time Context Loading** — Don't pre-load everything; use lightweight identifiers (file paths, queries) and load data at runtime via tools.
2. **Sub-Agent Architecture for Context Isolation** — Each subagent has clean context. Return only condensed summaries. Our framework already does this.
3. **Tool Result Clearing** — "One of the safest, lightest forms of compaction." Framework doesn't do this explicitly.
4. **Structured Note-Taking** — Write findings to persistent storage outside the context window. Our memory system supports this.
5. **Minimal Viable Tool Sets** — "Bloated tool sets create ambiguous decision points that waste context." Framework limits tools per agent.
6. **Right Altitude Balance** — Prompts should be "specific enough to guide behavior, flexible enough to provide heuristics."
7. **Code-Based Navigation** — Use bash/scripts for complex data extraction instead of reading entire files. 5-20x token savings for targeted operations vs full file reads.

## 7. Plan-Then-Clear Pattern

### The Problem

Long-running agents (especially head agents) accumulate exploration context, subagent results, and tool outputs. After 30-40 turns, context is mostly noise. Compaction is lossy. Lost-in-the-middle degrades recall of earlier findings.

### The Solution

**Phase 1: PLAN** — Agent explores, gathers context, synthesizes findings into a plan file on disk.
**RESET** — Context cleared (/clear for human-in-loop, subagent isolation for autonomous).
**Phase 2: EXECUTE** — Agent starts fresh, reads only the plan file (high-signal, curated), implements with full context budget.

### Two Modes

| | Human-in-Loop | Autonomous |
|---|---|---|
| Planning | Agent explores in session → writes plan to file | Head agent spawns Plan subagent → receives summary → writes plan |
| Context Reset | User runs /clear | Subagent context auto-discarded; new subagent starts fresh |
| Bridge | Plan file on disk | Plan file on disk (same) |
| Execution | Agent reads plan file, executes | Coding subagent reads plan file, executes |
| User Action | /clear between phases | None — subagent spawning handles it |

### Plan Discovery After /clear (Options B+C — DECIDED)

**Option B — Memory as plan pointer:**
Before /clear, agent writes to its persistent memory: "Current plan: docs/tasks/PLAN_auth.md — Status: approved"
After /clear, Recovery Instructions say "Read your agent memory." Agent picks up plan pointer.

**Option C — ACTIVE_PLAN.md marker file:**
Agent writes to `docs/ACTIVE_PLAN.md`:
```markdown
# Active Plan
- Path: docs/tasks/PLAN_auth.md
- Status: approved
- Created by: engineering-architect
- Phase: ready for execution
```
Add to CLAUDE.md Recovery Instructions: "Check docs/ACTIVE_PLAN.md for active plans."

Both mechanisms together provide redundancy.

### Which Agents Get This Pattern

- **Head agents (CPO, Architect, Design Lead, Business Strategist):** FULL pattern — plan-then-clear for complex tasks
- **Coding agents:** LIGHTWEIGHT — phase boundaries as compaction points, memory as working notes
- **Research/Review/Haiku agents:** NO pattern needed — short-lived, start fresh naturally

### /clear Known Issues (Documented)

- [GitHub #32871](https://github.com/anthropics/claude-code/issues/32871): Creates new session instead of clearing in place
- [GitHub #16189](https://github.com/anthropics/claude-code/issues/16189): Token counter doesn't reset in statusline
- [GitHub #2538](https://github.com/anthropics/claude-code/issues/2538): Some reports of partial context retention
- These are minor for our use case — core behavior (fresh context + files persist) works.

## 8. Context Introspection via Statusline

### How It Works

Claude Code's statusline receives full JSON after every assistant message including `context_window.used_percentage`. The script can write this to a temp file as a side effect. The agent reads the file to check its context budget.

### JSON Fields Available

```json
{
  "context_window": {
    "total_input_tokens": 90000,
    "total_output_tokens": 40000,
    "context_window_size": 200000,
    "used_percentage": 45,
    "remaining_percentage": 55,
    "current_usage": {
      "input_tokens": 8500,
      "output_tokens": 1200,
      "cache_creation_input_tokens": 5000,
      "cache_read_input_tokens": 2000
    }
  },
  "cost": {
    "total_cost_usd": 1.23,
    "total_duration_ms": 45000,
    "total_api_duration_ms": 2300
  },
  "model": { "id": "claude-opus-4-6", "display_name": "Opus" },
  "session_id": "abc123",
  "agent": { "name": "engineering-architect" }
}
```

### Context Budget Thresholds for Agent Decision-Making

| Usage | Action |
|-------|--------|
| Below 40% | Proceed normally |
| 40-60% | Externalize findings to disk proactively |
| 60-80% | Complete current task, compact or /clear before next major operation |
| Above 80% | STOP — write all state to disk, suggest /clear immediately |

Source: [Claude Code Statusline Docs](https://code.claude.com/docs/en/statusline)

## 9. Code-Based Navigation for Token Efficiency

### The Principle

Use computation to reduce context consumption. Instead of dumping raw file contents into the LLM's context, pre-process with code and inject only the distilled result.

### Examples

| Instead of... | Do this... | Token Savings |
|---------------|-----------|---------------|
| Read entire 400-line file | `grep -n "pattern" file.ts` | ~10x |
| Read 10 files to map dependencies | `python3 -c "extract imports script"` | ~20x |
| Read JSON config for one value | `jq '.specific.key' config.json` | ~50x |
| Read all test files to count tests | `grep -rc 'test\|it\|describe' tests/` | ~30x |
| Read file to check if function exists | `grep -c "functionName" file.ts` | ~100x |

### Guideline for Agents

- Use Grep/Glob (dedicated tools) for simple pattern lookups
- Use Bash with inline scripts for complex aggregation/transformation
- Use Python/Node scripts for multi-step data extraction from multiple sources
- Always prefer targeted extraction over full file reads
- Write extraction scripts to disk if reusable across multiple operations

## 12. Token Budget System — Deep Research (Added Late Session)

### Problem Statement

Agents operate blind — they don't know how many tokens a task will consume before starting, leading to mid-task compaction, context rot, and wasted expensive Opus tokens on exploration that should be delegated to Haiku.

### Token Counting Methods Available

**Method 1: Anthropic Token Count API (EXACT, FREE)**
- Endpoint: `POST /v1/messages/count_tokens`
- Python SDK: `client.messages.count_tokens(model="claude-opus-4-6", messages=[...])`
- Source: [Anthropic Token Counting Docs](https://platform.claude.com/docs/en/build-with-claude/token-counting)
- FREE to use, rate limited (100-8000 RPM by tier)
- Works with text, images, PDFs, tools — uses the REAL tokenizer
- Returns: `{"input_tokens": 14}`
- Requires `ANTHROPIC_API_KEY` in environment
- Note: `anthropic` Python SDK is NOT currently installed on user's system. Use `pip install anthropic` or fall back to heuristic.

**Method 2: Character-based heuristic (APPROXIMATE, OFFLINE)**
- English text: ~4 characters per token
- Code: ~3.5 characters per token
- Structured text (JSON, YAML): ~3 characters per token
- Accuracy: ~85-90% for most content
- Implementation: `wc -c file.ts` → divide by 3.5 for code
- No dependencies, instant, works offline

**Method 3: tiktoken (cl100k_base) — NOT recommended for Claude**
- OpenAI's tokenizer, close but not exact for Claude models
- Anthropic uses a different BPE tokenizer
- Would give misleading exact-looking but actually approximate results

### Recommended Architecture: Python Script + Haiku Agent

**Layer 1: `scripts/token-counter.py` (Deterministic Tool)**
- Input: list of file paths (as arguments or from a task file)
- Process: read each file, count tokens via API (if `anthropic` SDK available) or heuristic
- Output: JSON with per-file counts + total
- Example output:
```json
{
  "files": [
    {"path": "src/auth/middleware.ts", "bytes": 4200, "tokens": 1200},
    {"path": "src/auth/jwt.ts", "bytes": 3100, "tokens": 886}
  ],
  "total_tokens": 2086,
  "method": "heuristic",
  "pct_of_200k": 1.04
}
```
- Agents invoke via: `bash -c "python3 scripts/token-counter.py src/auth/*.ts src/models/user.ts"`
- This is the RELIABLE foundation — deterministic, no learning, always accurate for known files.

**Layer 2: `context-budget-analyst` Haiku Agent (Learned Estimator)**

```yaml
---
name: context-budget-analyst
description: Estimates context budget for tasks. Invoke before delegating coding work to predict if a task fits in a single context window.
model: haiku
tools: Read, Grep, Glob, Bash
memory: project
maxTurns: 25
---
```

What this agent does:
1. Reads the task file (or accepts file list)
2. Runs `token-counter.py` to get exact file token counts
3. Checks its memory for historical task data (if available)
4. Applies multipliers to estimate TOTAL context consumption:
   - File tokens (exact from script)
   - Tool overhead per file read (~200 tokens each)
   - Agent reasoning (~1500 tokens per decision point)
   - Edit/test cycles (~1500 tokens each)
   - System overhead (CLAUDE.md + agent prompt + tool defs ≈ 10,500 tokens, cached)
5. Returns estimate + recommendation:
   - "Task fits comfortably (est. 45% of budget)"
   - "Task is tight (est. 78% of budget) — consider splitting"
   - "Task will exceed budget (est. 140%) — MUST split into 2-3 subtasks"
6. After task completion (future): head agent records actual usage to analyst's memory

**Memory structure for the analyst agent:**
```markdown
## Calibration Data

### Project Averages
- Avg tokens per source file: ~1,100
- Avg tool overhead per read: ~250 tokens
- Avg edit/test cycle: ~1,800 tokens
- Backend implementation multiplier: file_tokens × 7.2 = total_tokens
- Frontend implementation multiplier: file_tokens × 5.5 = total_tokens
- Review multiplier: file_tokens × 2.3 = total_tokens

### Task History
| Task ID | Type | Files | File Tokens | Actual Total | Multiplier |
|---------|------|-------|-------------|-------------|------------|
| TASK_003 | backend | 8 | 11,250 | 82,000 | 7.3 |
| TASK_004 | frontend | 12 | 18,000 | 95,000 | 5.3 |
```

**Cold start behavior:** When memory is empty (new project), uses conservative defaults:
- Implementation tasks: file_tokens × 8 (conservative)
- Review tasks: file_tokens × 3
- Research tasks: file_tokens × 2
- These defaults are documented in the agent prompt

**Learning mechanism:** After 3-5 tasks, the agent recalculates project-specific multipliers from its history. No ML needed — simple average of (actual_total / file_tokens) per task type.

**Why agent over script:**
- Script can only count KNOWN files. Agent can ESTIMATE unknowns.
- Agent memory makes predictions project-specific and improving.
- Haiku agent costs ~$1/MTok — extremely cheap for a 25-turn estimation session.
- Head agents invoke it like any other subagent: `Agent(context-budget-analyst)`.
- Agent can also ADVISE on task splitting strategies based on budget analysis.

**Data flow for calibration (future enhancement):**
1. Head agent invokes context-budget-analyst before delegating task
2. Analyst returns estimate
3. Head agent delegates task to coding subagent
4. Coding subagent completes
5. Head agent reads statusline data (/tmp/claude-context-status.json) — BUT this shows HEAD agent's usage, not subagent's
6. For subagent tracking: add instruction to coding agents: "On completion, write your context percentage from the status bar to the task file's Result section"
7. Head agent records {task_id, estimate, actual} to analyst's memory

**Current limitation:** Subagent token usage isn't automatically captured. The statusline tracks the current session only. For V1.2, calibration data must be manually recorded or estimated. Automated subagent tracking is a future enhancement.

### Enriched Statusline Features (Beyond Basic Plan)

**Line 1 — Identity + Git:**
- Model name, agent name (if present), git branch (cached 5s)
- Color-coded: cyan for model, green for branch

**Line 2 — Context + Cost + Efficiency:**
- Context bar (10 chars, color-coded: green <60%, yellow 60-80%, red >80%)
- Context % AND absolute tokens remaining (e.g., "45% | 110k left")
- Session cost
- Duration
- Lines changed (+/-)
- Cache efficiency: `cache_read / (cache_read + input_tokens + cache_creation)` — shows what % of input is cached (higher = cheaper)

**Side-channel file (`/tmp/claude-context-status.json`):**
Write ALL useful fields for agent introspection:
```json
{
  "used_pct": 45,
  "remaining_pct": 55,
  "remaining_tokens": 110000,
  "window_size": 200000,
  "total_input": 90000,
  "total_output": 40000,
  "current_input": 8500,
  "cache_write": 5000,
  "cache_read": 2000,
  "cache_efficiency_pct": 23,
  "cost_usd": 1.23,
  "cost_per_min": 0.12,
  "duration_ms": 45000,
  "lines_added": 156,
  "lines_removed": 23,
  "model": "Opus",
  "model_id": "claude-opus-4-6",
  "agent": "engineering-architect",
  "session_id": "abc123",
  "exceeds_200k": false,
  "active_plan": true,
  "timestamp": "2026-03-13T14:30:00Z"
}
```

Note: `active_plan` is set by checking if `docs/ACTIVE_PLAN.md` exists. `remaining_tokens` computed from `window_size - (used_pct * window_size / 100)`. `cache_efficiency_pct` computed from current_usage fields. `cost_per_min` computed from `cost_usd / (duration_ms / 60000)`.

### Statusline Script Technical Notes

- Must handle null fields gracefully (early in session, fields may be null)
- Git operations cached to `/tmp/statusline-git-cache` (refresh every 5s) to avoid slowness
- Script runs after every assistant message, debounced at 300ms
- If script hangs or errors, statusline goes blank — keep it fast
- Test with: `echo '{"model":{"display_name":"Opus"},...}' | bash statusline.sh`
- `jq` is required dependency (installed on macOS via Homebrew, available on most Linux)
- Script should be installed by init.sh to project-level `.claude/hooks/statusline.sh` and referenced in project `.claude/settings.json`
- Does NOT overwrite user's global `~/.claude/settings.json` statusline (ccstatusline)
